Vault Enterprise

Namespaces: one cluster, many tenants

What a namespace is, when it earns its keep, and how access crosses the lines you draw. With a live environment to prove each point.

00 — Intro
01
Concept

A namespace is a small Vault inside your Vault

Each one carries its own auth methods, secrets engines, ACL and Sentinel policies, entities, groups and tokens. HashiCorp calls the result secure multi-tenancy.

The parent of every namespace is root, which is the Vault you get without the feature. Children nest as deep as you like, though three levels is the practical ceiling before the tree stops being readable.

# the tree this deck demos
root
├── platform/
│   ├── team-a/
│   └── team-b/
└── finance/
01 — Concept
02
Concept

Three rules explain everything that follows

1 Paths are relative

secret/foo with namespace platform/team-a and team-a/secret/foo with namespace platform reach the same key. Policies follow the same rule, so a policy in a parent can name a child by prefix.

2 Tokens travel down, never up or sideways

A token issued in platform/ works in platform/team-a. It does not work in finance/, and Vault will not look it up there, so the denial comes before any policy check.

3 Groups can hold entities from ancestors

A group in platform/team-a may list an entity that lives in platform/. When that entity's token makes a request in team-a, the group's policies apply to that request. vault token lookup shows them as external_namespace_policies.

01 — Concept
03
When

A namespace marks an administrative boundary

HashiCorp's own guidance is to use them sparingly. Create one when a tenant needs to run its own Vault, not when a team needs somewhere to put secrets.

Reach for a namespace when

  • A unit writes its own policies. A business unit with its own security team, a subsidiary, an external customer on a shared cluster.
  • Separation has to be shown. A regulated workload that auditors expect to see walled off, with its own audit trail per namespace.
  • Admin is delegated. A platform team hands a tenant the keys to create children, mounts and policies without a root operator in the loop.

Use paths and mounts instead when

  • It is one app or one team. An ACL policy on secret/data/team-x/* gives the isolation with none of the overhead.
  • Access is identity-shaped. Templated policies on entity metadata scale to hundreds of teams; hundreds of namespaces do not.
  • Shared services dominate. One Kubernetes auth mount or one LDAP mount in a parent beats a copy per child.
02 — When
04
Trade-offs

What you gain

1
cluster
One set of unseal keys, one licence, one audit pipeline, one upgrade. Tenants share the hardware and nothing else.
0
shared identity
Unrelated namespaces share no auth, no entities and no policies. A mistake in finance cannot leak into platform.
↓
inheritance
Shared services live once in a parent. Policies and identities in a parent reach down into its children by design.
self
service
A delegated admin creates children, mounts and policies inside their own tree. The root operator is out of the loop.

Path-relative design means a tenant's scripts and policies do not care where in the tree they sit.

03 — Trade-offs
05
Trade-offs

What it costs

  • Enterprise and HCP Vault Dedicated only. Community edition does not have the feature.
  • Every namespace uses storage. Each one starts with three mounts (auth, identity, system) and the whole namespace list must fit in a single storage entry. Mount tables cap at 1 MB on integrated storage.
  • Several sys/ paths stay root-only. Seal, rekey, raw storage and audit configuration among them. An administrative namespace gets a subset back.
  • Nothing goes up or sideways. Sharing between unrelated namespaces needs a cluster-wide switch or a copy of the secret.
  • Every client sets the namespace on every request. Forget it and you get a 403 that looks like a policy problem. chroot_namespace on a listener helps for single-tenant endpoints.

The environment: one shared tree and one tenant apart

root
├── platform/      userpass · entities alice, bob, carol · policy platform-admin
│   ├── team-a/    kv-v2 · policy team-a-kv · group team-a-devs (alice)
│   └── team-b/    kv-v2 · policy team-b-kv · group team-b-devs (bob)
└── finance/       userpass · entity frank · kv-v2 · group finance-readers

Single-node Vault Enterprise on Podman, Raft storage, auto-init and auto-unseal. The tree is built once on first start by provision.d/20-namespaces.sh.

The children have no auth mount of their own. finance/ has its own userpass and its own identity store and shares nothing with platform/.

04 — Demo
07
Demo · step 2

Log in once at the parent, work in the children

# alice authenticates where the mount is
vault write -namespace=platform \
  auth/userpass/login/alice password=...

# same token, child namespace: allowed
VAULT_NAMESPACE=platform/team-a \
  vault kv get secret/app/config

# what the token sees in team-a
vault token lookup
  policies                      [default]
  external_namespace_policies   {
    platform/team-a/: [team-a-kv] }

# sibling namespace: denied
VAULT_NAMESPACE=platform/team-b \
  vault kv get secret/app/config
  403 permission denied

alice's token has only default when it is issued. The team-a-devs group in the child lists her entity from platform/, so Vault adds team-a-kv to every request she makes in team-a.

team-b's group does not list her. Same token, same login, different answer. Membership is evaluated on every request, so no re-login is needed when it changes.

04 — Demo
08
Demo · step 2

Two ways to inherit, and they put the decision with different owners

child decides Group in the child namespace

team-a's admin writes team-a-kv and a group that lists alice's entity. The platform team never sees the change. This is the pattern in HashiCorp's secure multi-tenancy tutorial.

vault write -namespace=platform/team-a \
  identity/group name=team-a-devs \
  policies=team-a-kv \
  member_entity_ids=$ALICE_ID
parent decides Policy in the parent, child by prefix

carol's platform-admin policy is written in platform/. Vault reads its paths relative to that namespace, so team-a/* means platform/team-a/*. No group in either child.

# platform-admin, written in platform/
path "team-a/*" { capabilities = ["read", ...] }
path "team-b/*" { capabilities = ["read", ...] }

Neither approach needs an auth method mounted in the child.

09
Demo · step 3

finance/ shares nothing with platform/

# alice (platform token) in finance
VAULT_NAMESPACE=finance vault kv get secret/ledger/q4
  403 permission denied
VAULT_NAMESPACE=finance vault token lookup
  403 permission denied

# frank (finance token) at home, then in platform
VAULT_NAMESPACE=finance vault kv get secret/ledger/q4
  revenue   4,200,000
VAULT_NAMESPACE=platform/team-a vault kv get secret/app/config
  403 permission denied

# root namespace sees both
VAULT_NAMESPACE=finance vault kv get secret/ledger/q4
VAULT_NAMESPACE=platform/team-b vault kv get secret/app/config
  • The denial comes before any policy check. finance/ is outside alice's token sub-tree, so Vault refuses to look the token up at all.
  • Each tenant brings its own login. frank authenticates against the userpass mount in finance/ and his entity lives there.
  • Root is above everyone. Every namespace descends from root, so a root-namespace operator with the right policy reaches all of them. The isolation is between tenants rather than from the platform.

Demo · step 4

Three ways to cross a boundary, in rising order of blast radius

1
path prefix
Policy in a parent
carol, step 2. Scope is whichever child paths the parent policy names. Owner: the platform team.
2
ancestor entity
Group in the target, entity from above
alice joins team-b-devs and reads team-b with no new login. Scope is one group in one namespace. Owner: team-b's admin.
3
any namespace
Group in an unrelated namespace
alice joins finance-readers. Works only after a cluster-wide mode change. Owner: whoever owns the root namespace.

Demo · step 4

Option 3 is a cluster-wide switch, so decide it once

# default: groups only apply within a hierarchy
vault read sys/config/group-policy-application
  group_policy_application_mode  within_namespace_hierarchy

vault write sys/config/group-policy-application \
  group_policy_application_mode=any

vault write -namespace=finance \
  identity/group/name/finance-readers \
  member_entity_ids=$ALICE_ID

# alice, platform token, finance namespace
vault kv get secret/ledger/q4      # allowed

# put it back and the access goes with it
vault write sys/config/group-policy-application \
  group_policy_application_mode=within_namespace_hierarchy
vault kv get secret/ledger/q4      # 403
  • Introduced in Vault Enterprise 1.13. Before that, sibling access meant a copy of the secret or a second login.
  • It applies to every group in every namespace. You cannot enable it for finance alone. Decide it as a platform standard and write the decision down.
  • ACL policies only. Sentinel role governing policies are unaffected from 1.15.
  • It replicates. Primary and secondary clusters cannot run different modes.

Summary

What to take back to your design

  • Namespaces are for tenants who administer themselves. Everyone else gets a mount path and a templated policy.
  • Put shared auth in a parent and let the children pull identities down. One login point, access decided where the secrets live.
  • Unrelated tenants get unrelated trees. No shared ancestor below root means no accidental path across.
  • Pick the smallest crossing that works. Path prefix, then ancestor entity in a group, then the global mode. Each step widens who can grant what.
  • Codify the tree. Namespaces, policies and groups in Terraform, so the structure outlives the person who drew it.
